# ADR-001: Webアプリケーション構成

- Status: Accepted
- Date: 2026-09-28
- Updated: 2026-09-29
- Accepted: 2026-09-29

## Context

利用者はGit管理されたテスト仕様をブラウザで読み、同じ画面から結果を入力し、過去の実施履歴を確認したい。初期版は同一PC上で1人が利用する小規模な構成とし、仕様解析と履歴管理へ集中できるようにする。

テスト仕様ファイルがSource of Truthであり、Web UIには現在のファイル内容を直接表示する。実施結果は追記型の履歴としてSQLiteへ保存する。過去の仕様本文はGitで確認し、Webアプリケーション内では復元しない。

## Proposed Decision

- C# / .NET 10 LTSを使用する。
- ASP.NET Core Razor PagesでサーバーサイドWeb UIを作る。
- SQLiteとMicrosoft.Data.Sqliteを使用する。
- xUnitで自動テストを作る。
- V0.1ではフロントエンドとREST APIを分離しない。
- JavaScriptは表示切り替えなど操作性に必要な範囲へ限定する。
- `testman serve --specs <path>`をWebサーバーの起動入口とする方向で設計する。
- Web画面の表示時に現在のテスト仕様ファイルを直接読み込み、仕様本文をSQLiteへimportしない。
- SQLiteには実施結果、検証実施者名、仕様ファイル識別子、実施時点のGit commit SHAなど、履歴に必要な情報を保存する。
- V0.1はlocalhostだけで待ち受け、同一PCからのみ利用する。LAN公開は行わない。
- V0.1では認証・認可を設けない。
- Web UIからテスト仕様ファイルを編集しない。
- 過去の仕様本文はGitで確認し、Web UIでは復元表示しない。

## Rationale

Razor Pagesは、画面数の少ないフォーム中心のWebアプリを単一のC#ソリューションで構成できる。SPA、独立したAPI、別言語のビルド工程を導入せず、仕様解析、表示モードの切り替え、結果登録、履歴管理という対象へ集中できる。

テスト仕様をファイルから直接読むことで、Git管理された原本とWeb表示の同期操作が不要になる。SQLiteを結果保存へ限定することで、仕様と結果の責務を分離できる。

利用範囲をlocalhostへ限定することで、V0.1で認証・認可を設けずに同一PC上の利用へ集中できる。LAN公開や複数ユーザー利用はセキュリティモデルが異なるため、V0.1へ含めない。

## Consequences

- 配布物と依存関係を比較的少なくできる。
- UIとサーバー処理を同じソリューションでテストできる。
- 仕様変更は次回の画面表示へ反映でき、明示的なimport操作は不要になる。
- 仕様ファイルの解析エラーを、ファイルパスや行番号とともにWeb画面へ表示する必要がある。
- 結果登録時に実施時点のGit commit SHAを取得する必要がある。
- 仕様に未コミット変更がある場合の結果登録可否は別途決定する必要がある。
- SQLiteの実データファイルはGit管理せず、schemaとmigrationだけを管理する。
- localhost限定であっても、仕様由来の文字列はHTMLエスケープし、Markdown生成HTMLをサニタイズする必要がある。
- 高度なクライアント側操作が必要になった場合は再検討が必要になる。
- LAN公開や複数ユーザー対応を将来行う場合は、本ADRを見直し、認証、認可、CSRF、TLS、同時更新、監査を設計する必要がある。

## V0.1で採用しない構成

- LAN内の別端末または外部ネットワークへの公開
- SPAとREST APIの分離
- 外部DBサーバー
- 仕様本文のSQLiteへのimport
- Web UIからの仕様編集
- 認証・認可と複数ユーザー利用

## Acceptance Condition

ユーザーが、.NET 10、Razor Pages、SQLite、xUnit、localhost限定、仕様ファイル直接読込、仕様と結果の分離、およびV0.1で採用しない構成を承認した時点でAcceptedへ変更する。
