# 要求IDの採番ルール

## 対象

このリポジトリでは、要求IDを付ける「仕様」を、手順・期待結果・DBの状態・成果物・コードなどの証拠に照らして合否を判断できる記述と定義する。ブラウザから見える挙動だけには限定しない。判断基準が定まっていない「使いやすい」「小規模」などの目標や優先順位は、仕様として採番しない。必要なら検証条件を明確にしてから仕様にする。

現行の要求・詳細仕様である `requirements.md`、`web-ui.md`、`database.md`、`cli.md`、`test-format.md` の検証可能な要求にIDを付ける。見出し、背景説明、例、要求を再掲したスコープ一覧、対象外の列挙には新しいIDを付けない。検証対象でない設計意図や背景は、各文書の「設計意図・背景（要求IDなし）」など明示した節へ分け、その節の冒頭に検証対象の仕様ではないことを書く。`product-concept.md`、ADR、比較資料、未決事項は採番対象外とする。

## 形式と同一性

- 要求の定義箇所には `**REQ-0001**: 要求本文` の形式で記載する。番号は全対象文書を通じて一意とし、1から始まる10進数を少なくとも4桁にゼロ埋めする。
- 同じ要求を別の箇所で参照するときは既存IDを本文中に記載し、新しいIDを定義しない。上位要求に対する追加の検証可能な制約は、別の要求として採番できる。
- 要求の位置や文書名、表現だけが変わり、検証する内容が同じならIDを維持する。要求自体がなくなったら、そのIDは永久欠番とする。異なる要求に転用しない。
- 採番済みの記述が検証対象の仕様ではなかったと判明した場合は、仕様から外してIDを欠番とする。曖昧な記述を検証可能な条件へ明確化でき、要求の同一性が保たれる場合は元のIDを維持する。
- 一つの記述を分割・統合する際は、各IDが指す要求の同一性を確認する。同一性を維持できないIDは欠番とし、新しいIDを採番する。

## 次番号と変更確認

次に採番する番号: **REQ-0228**

- 新しい要求を追加するときは、この番号から順に割り当て、同じ変更で次番号を進める。削除や欠番が生じても次番号を戻さない。
- 次番号は現存する最大IDから再計算しない。削除済みIDを含む過去の採番はGit履歴で確認できる。
- 文書の変更確認時に、定義IDの形式、対象文書全体での重複、次番号との整合を確認する。並行した変更で同じIDが割り当てられた場合は、統合前に片方を未使用番号へ振り直し、次番号を更新する。
- 要求IDとテストケースの対応は [traceability.md](traceability.md) に記録する。対応を確認できない要求も同文書で明示する。
