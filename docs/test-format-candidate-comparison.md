# テスト仕様形式の候補サンプル比較

## この文書の位置づけ

本書は `docs/test-format-options.md` の案A、案B、案Cを、同じ内容で比較した記録であり、実装根拠ではない。案Aを基礎とする形式が採用され、正式な規則は `docs/test-format.md`、判断はAcceptedのADR-003に記録されている。

- [案A改: 見出し・共通条件・Markdown表](../testspecs/candidates/option-a-markdown-table.md)
- [案B: Markdownのテスト別セクション](../testspecs/candidates/option-b-markdown-sections.md)
- [案C: YAML](../testspecs/candidates/option-c-yaml.yaml)

案DのHTML tableは、許可タグとサニタイズ方針の設計が先に必要で、既存文書でもV0.1の標準形式にしない方向のため、今回の有力候補から除外した。

## 共通にした意味内容

各ファイルには、ログインテスト全体の概要と、正常ログイン、不正パスワード、空パスワードの3ケースを収録している。案A改はユーザーから示された利用イメージを確認するため、タイトルを見出し、その直後に「どのようなテストをするか」という概要を置く。前提条件は表全体の共通条件とし、各行を一意なIDを持つテストケースとして再構成した。大項目・中項目・小項目の3列も追加している。

案A改では、共通Stepsの任意の位置に「行別Stepsに記載があれば、それに従って操作する」と書ける。行別Stepsは任意であり、記載しない行は半角ハイフン1文字 (`-`) で示す。ログイン動作はtestmanの機能要件ではなく比較用の題材である。

## ユーザー確認済みの方向性

- `title`は表全体の見出しとする。
- titleごとに、詳細へ入る前にテストパターンの目的と範囲をレビューできる概要を必須とする。
- Preconditionsは見出しと表の間に置き、表内の全テストへ適用する。
- 行別Stepsの実施位置は、共通Steps内の文章で指示する。
- 行別Stepsは任意とし、記載がない場合は半角ハイフン1文字 (`-`) で示す。
- 共通Stepsから行別Stepsを参照する具体的な文章はツールで固定しない。
- 大項目、中項目、小項目に特に記載する内容がない場合は `-` で示す。
- ソースには通常のMarkdown表を使い、Web表示時に連続する同一の分類値をセル結合する。
- 分類列の `-` は連続していてもWeb表示でセル結合しない。
- 1つのTest IDは1つのテスト意図を表す。
- Expected Resultは原則IDごとに1つとし、同じテスト意図の範囲内では複数手順に対応する複数の期待内容を記載できる。
- 1つの仕様ファイルに、issueのスコープに応じて複数のTest IDを置ける。
- Test IDは仕様ファイル単位で一意とし、そのファイル内の最大番号の次を採番する。削除済みIDや欠番は再利用しない。

## 比較

| 観点 | 案A改: 見出し・共通条件・表 | 案B: テスト別セクション | 案C: YAML |
|---|---|---|---|
| 一覧性 | 高い。分類3列でも絞り込みやすい | 中程度。縦に長い | 中程度。完成時の表には見えない |
| 差分レビュー | 長い行の小変更を追いにくい | 手順単位で追いやすい | フィールド単位で追いやすい |
| 長文・複数行 | 共通条件・共通Stepsは書きやすい。行固有の長文はセル内記法が必要 | 比較的強い | 強いがYAML規則の理解が必要 |
| 操作と期待結果 | 共通Stepsが行別Stepsの実施位置を文章で指定し、結果は各行に記載する | 同じ行で対応する | 同じstep要素で対応する |
| 段階的レビュー | 概要と分類表を先に確認し、詳細へ進める | 概要の後にケース単位で詳細を確認できる | 概要と詳細の構造は明確だが、完成形で確認しにくい |
| 人手編集 | 短いケースには簡潔 | Markdown利用者には自然 | インデントに注意が必要 |
| 厳密な検証 | 独自の表検証が必要 | 見出しと表の検証が必要 | スキーマ検証を行いやすい |
| 安全なWeb表示 | Markdown機能制限とサニタイズが必要 | Markdown機能制限とサニタイズが必要 | 値をエスケープして専用UIへ描画しやすい |
| 拡張・互換性 | 列追加の影響が大きい | セクション追加規則が必要 | バージョンとスキーマを導入しやすい |
| 表計算ソフトとの往復 | 3案では最も近い | 手順表だけは行いやすい | 向かない |

## 採用時に明文化が必要な規則

### 案A

- 見出しが表す範囲と、1ファイル内に置ける見出し・表の数
- Overviewの見出し名、許可するMarkdown、文章量
- PreconditionsおよびCommon stepsが適用される表の範囲
- ID、大項目、中項目、小項目、Expected resultの必須・任意
- Steps列で `-` 以外の空欄をエラーにするか
- 改行、縦棒、Markdown、コードのエスケープ

### 案Aのセル結合に関する比較

| 方法 | Git上の見え方 | 解析の明確さ | 編集時の安全性 | Web表示 |
|---|---|---|---|---|
| 同じ値を各行に記載 | 重複して見える | 高い | 行を単独で移動しやすい | 連続する同一値を結合可能 |
| 拡張記号で直前セルへ結合 | 重複が少ない | 継承規則が必要 | 行の移動・挿入で意味が変わりうる | 対応プレビューへの固定が必要 |
| HTML `rowspan` | 結合を直接表現 | HTML解析が必要 | 手編集しにくい | 直接結合できるがサニタイズが必要 |

採用した方式では、ソースに同じ分類値を各行に記載し、testmanのWeb表示時だけ連続する同一値を結合する。通常のMarkdownプレビューとの互換性と、各行が単独で意味を持つ性質を保てる。分類値ではない `-` は結合対象外とする。

### 案B

- ケースを表す見出しレベルとID・タイトルの解析
- 必須・任意セクション
- Steps表の列名、列順、空欄、連番
- 自由見出しと予約見出しの区別、および許可するMarkdown

### 案C

- ルート構造、必須・任意・未知フィールド
- YAMLアンカー、タグ、複数ドキュメントの可否
- 暗黙の型変換を避ける読み込み規則
- スキーマバージョンと説明文でのMarkdownの可否

## 評価結果

案A改を正式形式の基礎として採用する。見出しと共通記述で重複を避けながら、一意なIDを持つケースを表で一覧でき、概要から詳細へ段階的にレビューできるためである。

- 案Bはケース単位の説明に利点があるが、一覧性と今回の運用イメージが案Aより弱いため採用しない。
- 案Cは厳密な機械処理に利点があるが、Markdownとしてのレビュー性が案Aより弱いため採用しない。

## 検討時の未決事項

1. Overview、Preconditions、Common steps、表セルで許可するMarkdownと改行記法。
2. Test IDの具体的な文字列形式と、既存IDの変更可否。
3. 重複ID、未知・欠落項目、不正入力を全件拒否するか、正常分だけ扱うか。
4. 形式バージョンと将来の互換性・移行方針。

これらはすべてユーザー確認済みであり、回答は `docs/test-format.md` とADR-003へ反映済みである。
