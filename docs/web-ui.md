# Web UI 方針

## 状態

初期ドラフト。画面構成と入力項目はユーザー確認後に確定する。

## 基本方針

- サーバーサイドでHTMLを生成するシンプルなWeb UIを第一候補とする。
- テスト実施者が仕様を読みながら結果を入力しやすいことを優先する。
- 詳細な実施内容へ入る前に、テストパターンの概要をレビューできるようにする。
- V0.1ではWeb画面から仕様ファイルを編集しない。
- 画面表示時には、現在のテスト仕様ファイルを原本として直接読み込む。SQLiteへimportした仕様本文を表示元にしない。
- JavaScriptへの依存は、操作性に必要な範囲へ抑える。

## 画面候補

### 表示モード

同じテスト仕様について、次の表示を切り替えられるようにする。

- テストパターン表示: title、概要、大項目、中項目、小項目を表示し、「どのようなテストをするか」をレビューする。Test IDとPreconditionsは表示しない。
- 検証実施表示: Test ID、前提条件、共通Steps、行別Steps、Expected Result、結果入力を表示し、実際の検証に使用する。

表示モードの切り替えは仕様データを変更せず、同じテストケースを異なる詳細度で表示する。

### テスト一覧

- Test ID
- タイトル
- 所属する仕様ファイルまたはグループ
- 最新結果（採用するかは未決）
- 最終実施日時（採用するかは未決）

### テスト詳細・実施

- Test IDとタイトル
- 前提条件
- 手順
- 期待結果
- Pass / Failの選択
- コメント
- 検証実施者名
- 登録操作

誤操作防止のため、結果登録前の確認が必要かは実際の操作感を見て決める。

### 実施履歴

- 実施日時
- 結果
- コメント
- 検証実施者名
- 実施時点のGit commit SHA

過去の仕様本文はGitで確認する。Web UIはGit commit SHAを追跡情報として表示するが、そのリビジョンの仕様本文を復元表示しない。

## エラー表示

- 仕様ファイルのパス、可能なら行番号、エラー理由を表示する。
- 診断を画面上部へ目立つ形で一覧表示する。
- 正常に解析できたtitleは表示を継続し、解析できないtitleは理由を表示する。
- 重複IDまたは安全に識別できない行は表示してよいが、結果登録を無効化する。
- 利用者の入力エラーとシステム障害を区別する。
- DB保存に失敗した場合、成功したように見せない。
- 内部例外やスタックトレースを通常画面へそのまま表示しない。

## セキュリティ

- GitHub Flavored Markdown相当の記法と生HTMLを入力として許可する。
- Markdownから生成したHTMLと生HTMLは、`docs/test-format.md` の許可リストでサニタイズする。
- `script`、危険な埋め込み要素、イベント属性、危険なURLなど、許可リスト外の内容を除去する。
- V0.1の待受アドレスはlocalhostに限定し、同一PCからだけ利用する。
- 外部公開や複数人利用が必要になった場合は、認証、CSRF、権限、TLSを改めて設計する。
